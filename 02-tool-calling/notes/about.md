# Tool Calling + Agentic AI — My Notes

## 1. What is Tool Calling?

**Tool Calling** means giving an AI model access to specific functions/tools that it can request when it needs external information or an action.

Instead of the LLM trying to answer everything from its own knowledge:

```text
User
 ↓
LLM
 ↓
LLM decides: "I need employee data"
 ↓
Tool Call
 ↓
Python Function
 ↓
Tool Result
 ↓
LLM
 ↓
Final Answer
```

### Simple example

User asks:

> What is employee 102's leave balance?

The LLM doesn't know the actual employee balance.

So it decides:

```text
get_leave_balance(employee_id="102")
```

Python executes the function and returns:

```json
{
  "employee_id": "102",
  "remaining_leaves": 8
}
```

Then the LLM converts that result into:

> Employee 102 has 8 days of leave remaining.

---

# 2. Why do we need Tool Calling?

An LLM by itself is mainly a **reasoning/generation system**.

It does not automatically have access to:

* Company database
* Employee information
* Bank account
* Stock prices
* Weather
* APIs
* Internal systems
* File systems
* Business operations

Tools allow the LLM to interact with these systems.

For example:

```text
LLM
 │
 ├── Database Tool
 ├── REST API Tool
 ├── Calculator Tool
 ├── Search Tool
 ├── Email Tool
 └── Company Knowledge Tool
```

The LLM decides **which tool is appropriate**.

# 4. Our Tools

We created two employee tools.

### Tool 1 — `get_leave_balance()`

```python
def get_leave_balance(employee_id):
    employees = {
        "101": 12,
        "102": 8,
        "103": 15
    }

    return {
        "employee_id": employee_id,
        "remaining_leaves": employees.get(employee_id, 0)
    }
```

This tool returns an employee's remaining leaves.

---

### Tool 2 — `get_wfh_days()`

```python
def get_wfh_days(employee_id):
    wfh_data = {
        "101": 1,
        "102": 2,
        "103": 0
    }

    return {
        "employee_id": employee_id,
        "wfh_days_used": wfh_data.get(employee_id, 0)
    }
```

This returns how many WFH days the employee has used during the current week.

---

# 5. `TOOLS` Dictionary

We created:

```python
TOOLS = {
    "get_leave_balance": get_leave_balance,
    "get_wfh_days": get_wfh_days
}
```

This acts like a **tool registry**.

It maps the tool name generated by the LLM to the actual Python function.

For example:

```text
"get_leave_balance"
        ↓
get_leave_balance()
```

---

# 6. Tool Definitions

The Python function alone isn't enough.

The LLM needs to know:

* What tools are available?
* What does each tool do?
* What parameters does it require?

Therefore we created **tool definitions**.

For example:

```text
Tool name:
get_leave_balance

Description:
Get the current leave balance of a specific employee.

Parameter:
employee_id → string
```

This is essentially telling Gemini:

> "These are the functions you are allowed to request."

---

# 7. Important Difference

There are two separate things:

### Tool Definition

Tells the LLM **what the tool is**.

```text
get_leave_balance
employee_id
description
```

### Tool Implementation

Actually performs the operation.

```python
def get_leave_balance(employee_id):
    ...
```

So:

```text
Tool Definition
      ↓
LLM understands tool
      ↓
LLM requests tool
      ↓
Python implementation executes
```

# 8. Tool Executor

We created `tool_executor.py`.

Its job is to safely execute the requested tool.

Conceptually:

```python
def execute_tool(function_name, tool_arguments):

    if function_name not in TOOLS:
        return error

    tool_function = TOOLS[function_name]

    result = tool_function(**tool_arguments)

    return result
```

This is important because we **don't directly execute arbitrary functions requested by the LLM**.

We first check:

```python
if function_name not in TOOLS:
```

Therefore, only registered tools can be executed.

```text

```

Now the Agent can decide:

> "This question is about company policy, so I should search the company knowledge."

Therefore:

```text

 ↓

 ↓
RAG
 ↓
Vector Store
 ↓
Relevant Documents
 ↓
Gemini
 ↓
RAG Answer
 ↓
Agent
```

This is a key transition from a simple RAG application toward an **agentic system**.

# 11. Agent Loop

Our agent works approximately like this:

```text
                    ┌───────────────┐
                    │  User Question│
                    └───────┬───────┘
                            ↓
                    ┌───────────────┐
                    │    Gemini     │
                    └───────┬───────┘
                            ↓
                 Does it need a tool?
                     /           \
                   No             Yes
                   ↓               ↓
              Final Answer     Tool Call
                                   ↓
                            Tool Executor
                                   ↓
                              Tool Result
                                   ↓
                                Gemini
                                   ↓
                            Final Answer
```

The important concept is:

> **The LLM controls the decision, while Python controls the actual execution.**

# 13. Tool Result Goes Back to the LLM

A very important concept:

The tool does **not** directly give the final answer to the user.

Instead:

```text
User
 ↓
LLM
 ↓
Tool
 ↓
Tool Result
 ↓
LLM
 ↓
Final Answer
```

For example:

```text
Tool Result:
8 leaves
```

The LLM can then produce:

> You currently have 8 days of leave remaining.

So the LLM is responsible for **reasoning + natural-language response**, while the tool provides **real data/action**.

# 15. Agent vs Normal Chatbot

### Normal chatbot

```text
User
 ↓
LLM
 ↓
Answer
```

The LLM mostly generates a response.

### RAG chatbot

```text
User
 ↓
Retriever
 ↓
Documents
 ↓
LLM
 ↓
Answer
```

The system retrieves relevant information.

### Tool-Calling Agent

```text
User
 ↓
LLM
 ↓
Decision
 ↓
Tool
 ↓
Result
 ↓
LLM
 ↓
Answer
```

The LLM can decide what action/information it needs.

### Agentic RAG

Our system combines them:

```text
                    User
                      ↓
                    Agent
                      ↓
          ┌───────────┴───────────┐
          ↓                       ↓
   Employee Tools            RAG Tool
          ↓                       ↓
 Employee Data             Company Documents
          └───────────┬───────────┘
                      ↓
                    Agent
                      ↓
                 Final Answer
```

Endpoint:

```text
POST /ask
```

Request:

```json
{
  "question": "How many leaves does employee 102 have?"
```

FastAPI calls:

```python
run_agent(request.question)
```

```json
{
  "question": "How many leaves does employee 102 have?",

}
```

So our architecture became:

```text
Frontend / Client
       ↓
    FastAPI
       ↓
     Agent
       ↓
     Gemini
       ↓
 Tools / RAG
       ↓
     Results
       ↓
     Gemini
       ↓
    Response
```

# 19. Most Important Concepts to Remember

### Concept 1

**LLM decides, application executes.**

```text
LLM → "Call get_leave_balance"
Python → actually executes it
```

### Concept 2

**Tool definition ≠ tool implementation**

Definition tells the model what exists.

Implementation actually performs the work.

### Concept 3

**Tool results go back to the LLM**

The LLM uses the result to produce the final response.

### Concept 4

**An agent can call multiple tools**

One question can require:

```text
Tool A
+
Tool B
+
RAG
```

### Concept 5

**RAG can itself be a tool**

This allows the agent to decide when company knowledge needs to be retrieved.

### Concept 6

**The agent works in a loop**

```text
Think/Decide
    ↓
Tool
    ↓
Observe Result
    ↓
Think/Decide
    ↓
Final Answer
```

This loop is one of the foundations of **Agentic AI**.

---

# 20. Tool Calling vs Agentic AI

Don't confuse these two.

### Tool Calling

A model calls a predefined function.

```text
LLM → Tool → Result
```

### Agentic AI

The system can make decisions over multiple steps.

```text
Goal
 ↓
Decide
 ↓
Tool
 ↓
Observe
 ↓
Decide again
 ↓
Another Tool
 ↓
Observe
 ↓
Final Answer
```

So:

> **Tool Calling is one of the building blocks of Agentic AI.**

Our project started with Tool Calling and then evolved into an **Agentic RAG system**.
